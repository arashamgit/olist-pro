## ۱. نقش‌ها و شناسه‌ها

| شناسه | نقش اصلی | حوزه مسئولیت |
| :--- | :--- | :--- |
| **Member A** | مالک داده و زیرساخت | فهرست داده، شناخت، روابط، پاک‌سازی، ویژگی‌ها، تحلیل سفارش‌ها |
| **Member B** | تحلیل تجربه مشتری | مشتریان و جغرافیا، پرداخت، رضایت، تأخیر و رضایت |
| **Member C** | تحلیل محصول و عملیات | محصولات، عملکرد ارسال، فروشندگان |
| همه اعضا | کار مشترک | تحلیل‌های ترکیبی، بازبینی، یافته‌های نهایی، گزارش، کنترل کیفیت، ZIP |

> این شناسه‌ها موقت‌اند و پیش از تحویل با نام واقعی اعضا جایگزین می‌شوند.
> قاعده مهم: **هیچ‌کس مستقیماً روی `main` کار نمی‌کند.**

## ۲. چرا تقسیم کار مساوی نیست؟

تقسیم ساده ۱۳ نوتبوک به سه بخش مساوی ناعادلانه است، چون پیچیدگی بخش‌ها یکسان نیست:

- بخش Member A شامل ساخت زیرساخت مشترک است (`config`, `data_loader`,
  `data_quality`, `cleaning`, `features`) که هر سه عضو به آن وابسته‌اند و حجم
  کارش بیش از یک نوتبوک معمولی است.
- بخش Member B شامل دو حوزه پرحجم (رضایت و تأخیر-رضایت) و اتصال‌های حساس
  (کاهش نظرات) است.
- بخش Member C شامل سه نوتبوک تحلیلی و پایه دو تحلیل ترکیبی است.

تقسیم‌بندی زیر بر پایه **حجم واقعی کار و وابستگی فنی** انجام شده است، نه تعداد
نوتبوک. تعداد نوتبوک هر عضو (۳، ۴، ۳ به‌علاوه زیرساخت) این نامتوازنی را جبران
می‌کند.

## ۴. قواعد Git (الزامی برای همه اعضا)

۱. هیچ‌کس مستقیم روی `main` کامیت نمی‌کند.
۲. پیش از شروع کار: `git checkout main` و `git pull origin main`.
۳. برای هر وظیفه یک شاخه با نام‌گذاری مشخص ساخته می‌شود.
۴. پیش از هر کامیت: `git status` و `git diff` بررسی می‌شود.
۵. کامیت‌ها کوچک و با پیام Conventional Commits هستند.
۶. هر شاخه به GitHub پوش می‌شود.
۷. ادغام فقط با Pull Request و پس از بازبینی حداقل یک عضو دیگر.
۸. آزمون‌ها پیش از ادغام اجرا می‌شوند.
۹. مکث در کار (Work In Progress) با PR به‌صورت Draft ثبت می‌شود.
۱۰. شاخه پس از ادغام حذف می‌شود و کار بعدی از `main` به‌روز شاخه می‌گیرد.

### الگوی نام‌گذاری شاخه

```text
chore/project-setup

feat/feature-engineering
feat/order-analysis
feat/customer-analysis

```

### الگوی پیام کامیت (Conventional Commits)

```text
chore: pin analysis dependencies
docs: add project charter and data dictionary
feat: add data inventory notebook
feat: implement order trend analysis
fix: correct delivery delay calculation to calendar dates
test: add payment metric validation
refactor: centralize date feature generation
chore: update deliverables archive
```

قاعده مهم: **پیام کامیت باید با تغییر واقعی انجام‌شده مطابقت داشته باشد.**
هیچ کامیت یا فعالیتی به نام عضوی که آن کار را انجام نداده است ثبت نمی‌شود.

## ۵. مدیریت نوتبوک‌ها (تعارض‌زدایی)

فایل‌های `.ipynb` در ادغام هم‌زمان به‌شدت تعارض‌پذیرند. برای کاهش دردسر:

۱. **هر نوتبوک یک مالک اصلی دارد** (جدول بخش ۳).
۲. هیچ عضوی نوتبوک عضو دیگر را ویرایش نمی‌کند؛ بازخورد در PR نوشته می‌شود.
۳. منطق مشترک در `src/olist_analysis/` می‌ماند؛ نوتبوک‌ها فقط فراخوانی و تفسیر
   می‌کنند. بنابراین تعارض نوتبوک تقریباً همیشه صفر است.
۴. پیش از درخواست ادغام، هر عضو نوتبوک خود را مستقل و از ابتدا اجرا می‌کند
   (Kernel → Restart & Run All) و خروجی‌ها را ذخیره می‌کند.
۵. اگر تعارض رخ داد، مالک نوتبوک آن را حل می‌کند و همه سلول‌ها را از نو اجرا
   می‌کند.
۶. فایل `.gitattributes` پروژه نرمال‌سازی خط (LF) را فعال می‌کند تا دیف‌های ویندوز
   و لینوکس بی‌دلیل تغییر نکنند.

## ۶. سیاست نگهداری داده‌ها در مخزن

| مورد | تصمیم |
| :--- | :--- |
| داده خام در Git | در این مخزن حاضر است (تصمیم قبلی پروژه) و تاریخچه آن حفظ می‌شود |
| داده میانی و پردازش‌شده | در `.gitignore` (قابل بازتولید و بزرگ) |
| کش parquet | در `.gitignore` |
| فایل‌های ZIP تحویل | در `.gitignore` |
| کلید و رمز | هرگز در مخزن قرار نمی‌گیرد (هیچ کلیدی مورد نیاز نیست) |

توضیح: قرار داشتن فایل در `.gitignore` تنها از کامیت معمول جلوگیری می‌کند و به
خودی‌خود دسترسی محلی را از بین نمی‌برد؛ برعکس، حذف فایل از `.gitignore` هم به‌تنهایی
آن را منتشر نمی‌کند. جزئیات مسیر و تأیید داده در `data/README.md` آمده است.

## ۷. معیارهای بازبینی Pull Request

بازبین هر PR باید این موارد را بررسی و در PR تأیید کند:

۱. تعداد ردیف گرین‌ها تغییر نکرده است (خروجی `git diff` روی اعداد کلیدی).
۲. هر نسبت تازه، مخرج صریح دارد.
۳. اگر اتصال تازه‌ای اضافه شده، نوع رابطه اعلام شده است.
۴. نمودارها عنوان، برچسب محور و واحد دارند.
۵. متن تفسیر با اعداد جدول انطباق دارد.
۶. نوتبوک از ابتدا اجرا شده و خطا ندارد.
۷. `python -m pytest -q` سبز است.
۸. هیچ فایل موقت، کش یا داده حساس کامیت نشده است.
