# مرحله ۱ - راه‌اندازی مخزن و قاعده کار تیمی

<div dir="rtl" align="right">

## ۱. هدف مرحله

تثبیت قاعده‌های کار با Git پیش از شروع توسعه، تا وقتی سه نفر هم‌زمان کار می‌کنند
هیچ تغییری از بین نرود و `main` همیشه نسخه پایدار و قابل بررسی باشد.

## ۲. مسئول اصلی و بازبین

- مسئول اصلی: **Member A**
- بازبین: **Member C**
- تأییدکننده: هر سه عضو (چون قاعده مشترک است)

## ۳. پیش‌نیازها

- مرحله ۰ کامل شده باشد
- دسترسی نوشتن به مخزن GitHub

## ۴. شاخه Git

شاخه‌ای برای این مرحله لازم نیست اگر مستندات را در همان `chore/project-setup`
می‌نویسید. در غیر این صورت:

```bash
git checkout -b docs/project-charter
```

## ۵. فایل‌های موردنیاز

| فایل | کار |
| :--- | :--- |
| `docs/project_charter.md` | منشور پروژه |
| `docs/team_workflow.md` | گردش کار Git و تقسیم وظیفه‌ها |
| `docs/project_roadmap.md` | نقشه راه و برنامه زمانی |
| `.gitattributes` | نرمال‌سازی خط (LF) برای جلوگیری از دیف بی‌دلیل |
| `docs/analysis_log.md` | رکورد زنده کار انجام‌شده |

## ۶. محتوای مورد انتظار

**`docs/team_workflow.md`** باید شامل این موارد باشد:

۱. جدول نقش‌ها (Member A، B، C) و حوزه مسئولیت هرکدام
۲. دلیل اینکه تقسیم کار **مساوی نیست** (زیرساخت فاز ۰ تا ۲ بار سنگین‌تری دارد)
۳. جدول وظیفه‌ها با این ستون‌ها برای هر وظیفه: هدف، مسئول، بازبین، پیش‌نیاز،
   فایل‌ها، شاخه، خروجی، آزمون، معیار پذیرش، وابستگی
۴. ده قاعده الزامی Git
۵. الگوی نام‌گذاری شاخه و الگوی پیام کامیت (Conventional Commits)
۶. سیاست مدیریت نوتبوک‌ها برای کاهش تعارض
۷. سیاست نگهداری داده در مخزن
۸. هشت معیار بازبینی Pull Request
۹. نقاط همگام‌سازی تیمی (T0 تا T4)

**`docs/project_roadmap.md`** باید برای هر مرحله تخمین حجم کار، مسئول، بازبین،
وابستگی، خروجی، معیار پذیرش و ریسک داشته باشد، مسیر بحرانی را مشخص کند و توضیح
دهد چرا فاز ۲ گلوگاه پروژه است.

## ۷. دستورات ترمینال

### ویندوز (PowerShell)

```powershell
# بررسی وضعیت پیش از شروع
git status
git log --oneline -5
git branch --show-current

# دریافت آخرین نسخه main
git checkout main
git pull origin main

# ساخت شاخه این مرحله
git checkout -b docs/project-charter
```

### بازبینی تغییرات پیش از کامیت

```bash
git status
git diff
git diff --stat
```

## ۸. آزمون‌ها

این مرحله کد ندارد، پس آزمون خودکار ندارد. کنترل دستی الزامی:

```bash
git diff --name-only            # فهرست فایل‌های تغییر‌یافته
git log --oneline -3
```

مطمئن شوید هیچ فایلی خارج از دامنه این مرحله تغییر نکرده است.

## ۹. خروجی مورد انتظار

- چهار فایل مستندات ساخته‌شده و بازبینی‌شده
- `.gitattributes` با نرمال‌سازی خط فعال
- جدول وظیفه‌ها با مسئول و بازبین مشخص برای هر وظیفه (هیچ وظیفه‌ای با عبارت مبهم
  «تحلیل را انجام بده» تعریف نشده باشد)

## ۱۰. پیام Commit پیشنهادی

```text
docs: add project charter, team workflow and roadmap

- define the three-member split based on real workload, not notebook count
- document mandatory Git rules, branch naming and commit conventions
- record acceptance criteria, dependencies and risks for every phase
```

## ۱۱. Push و Pull Request

```bash
git add docs/project_charter.md docs/team_workflow.md docs/project_roadmap.md \
        docs/analysis_log.md .gitattributes
git commit -m "docs: add project charter, team workflow and roadmap"
git push -u origin docs/project-charter
```

PR را بسازید و در توضیحات آن بنویسید کدام عضو مسئول کدام وظیفه است.

## ۱۲. مواردی که بازبین باید کنترل کند

۱. هر وظیفه مسئول و بازبین مشخص دارد و معیار پذیرشش عینی است.
۲. هیچ وظیفه‌ای بدون پیش‌نیاز و وابستگی تعریف نشده باشد.
۳. قاعده «هیچ‌کس مستقیم روی main کامیت نمی‌کند» صریح نوشته شده باشد.
۴. الگوی پیام کامیت واقع‌بینانه و مطابق تغییرات باشد.
۵. سیاست داده (ورود یا عدم ورود داده خام به Git) صریح و بدون تناقض باشد.
۶. هیچ تاریخ ساختگی یا فعالیت جعلی به اعضا نسبت داده نشده باشد.

## ۱۳. معیار پذیرش

- [ ] جدول وظیفه‌ها کامل و بدون ابهام است
- [ ] همه اعضا نام شاخه خود را در PR یا مستند می‌بینند
- [ ] ده قاعده Git نوشته شده است
- [ ] معیار بازبینی PR فهرست شده است
- [ ] PR تأیید و ادغام شده و شاخه حذف شده است

## ۱۴. شرط شروع مرحله بعد

پیش از شروع مرحله ۲، هر سه عضو باید با شاخه‌سازی، کامیت و ساخت PR حداقل یک بار
تمرین کرده باشند (می‌تواند با یک کامیت کوچک مستنداتی باشد). اگر قاعده‌ها جا
نیفتاده باشد، تعارض‌های مراحل بعدی وقت زیادی می‌گیرد.
