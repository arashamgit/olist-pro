## ۲. هر فایل از کجا تهیه می‌شود؟

- **مسیر اول (وضعیت فعلی):** فایل‌ها از قبل در همین مخزن و در `data/raw/`
  قرار دارند و در تاریخچه Git ثبت شده‌اند. اگر مخزن را کلون کنید، فایل‌ها
  همراه آن می‌آیند و نیازی به کار دیگری نیست.
- **مسیر دوم (دریافت مجدد):** این مجموعه، دیتاست عمومی «Brazilian E-Commerce
  Public Dataset by Olist» است که در Kaggle منتشر شده است. اگر لازم شد داده
  بازسازی شود، همان نسخه منتشرشده را دریافت کنید و نام فایل‌ها را **بدون تغییر**
  در `data/raw/` قرار دهید.
- **دریافت داده مستقل از کد:** هیچ بخشی از کد تحلیل، داده را دانلود نمی‌کند.
  دریافت داده یک گام دستی و مستقل است؛ کد فقط فایل‌های `data/raw/` را می‌خواند.

## ۳. مسیر مورد انتظار فایل‌ها

```text
olist-pro/
└── data/
    ├── raw/            ← ۹ فایل CSV اصلی (ورودی، دست‌نخورده)
    ├── interim/        ← کش parquet و فایل‌های میانی (در Git نیست)
    └── processed/      ← گرین‌های تحلیلی آماده (در Git نیست)
```

ساختار پوشه‌ها به‌صورت خودکار در اولین اجرای کد ساخته می‌شود.

## ۴. کنترل‌های تأیید کامل بودن داده

پس از قرار دادن فایل‌ها، این دستور را اجرا کنید:

```bash
python scripts/validate_data.py
```

این اسکریپت ۲۲ بررسی انجام می‌دهد و در صورت مشکل با کد خروجی غیرصفر متوقف
می‌شود. بررسی‌های اصلی:

| کنترل | مقدار انتظار |
| :--- | :--- |
| حضور هر ۹ فایل | همه موجود |
| حجم کل | بیش از ۱۰۰ مگابایت |
| تعداد سطر جدول سفارش‌ها | ۹۹٬۴۴۱ |
| تعداد سطر ژئولوکیشن | ۱٬۰۰۰٬۱۶۳ |
| برابر بودن سطر سفارش و مشتری | برابر (۹۹٬۴۴۱) |
| یکتایی کلید اصلی ۷ جدول | یکتا (کلید جدول نظرات مستثناست) |
| شناسه یتیم در ۶ رابطه | صفر |
| تبدیل همه زمان‌ها | بدون خطا |
| دامنه امتیاز نظر | ۱ تا ۵ |
| ماه‌های پیوسته پنجره تحلیلی | ۲۰ ماه |

اگر هر بررسی شکست خورد، علت همان‌جا چاپ می‌شود و باید فایل مربوطه دوباره
دریافت شود.

### کنترل جایگزین سریع (بدون اجرای اسکریپت)

```bash
wc -l data/raw/*.csv
```

توجه: تعداد خط فیزیکی فایل نظرات (۱۰۴٬۷۲۰) با تعداد ردیف منطقی آن (۹۹٬۲۲۴)
متفاوت است، چون متن بعضی نظرات شامل خط جدید است. مبنای محاسبات، ردیف منطقی است.

## ۵. چگونه نسخه داده مورد استفاده ثبت و کنترل می‌شود؟

۱. **اثر انگشت فایل:** جدول `reports/tables/01_file_inventory.csv` برای هر فایل،
   حجم دقیق به بایت و ۱۶ کاراکتر اول SHA-256 را ثبت می‌کند. هر تغییر در داده،
   این جدول را تغییر می‌دهد.
۲. **مهر زمانی منبع:** کش parquet در `data/interim/cache/_fingerprints.json`
   اندازه و زمان تغییر هر فایل خام را نگه می‌دارد. اگر فایل خام عوض شود، کش
   **خودکار باطل** می‌شود و داده قدیمی هرگز بی‌صدا استفاده نمی‌شود.
۳. **مهر زمانی مجموعه تحلیل:** `data/processed/_manifest.json` تعداد ردیف هر
   گرین تحلیلی و مهر زمانی همه فایل‌های خام را ثبت می‌کند.
۴. **بازسازی کنترل‌شده:** `python scripts/run_all.py` کل زنجیره را از صفر
   بازمی‌سازد:

```bash
python scripts/run_all.py            # خط لوله + نوتبوک‌ها + گزارش + آزمون‌ها
python scripts/run_all.py --quick    # فقط خط لوله + گزارش
```

## ۶. سیاست نگهداری داده (و مقایسه گزینه‌ها)

| گزینه | مزیت | عیب | تصمیم |
| :--- | :--- | :--- | :--- |
| نگهداری محلی و نادیده‌گرفتن با Git | مخزن سبک می‌ماند | هر عضو باید داده را جدا تهیه کند | برای داده‌های میانی و پردازش‌شده انتخاب شد |
| دریافت از منبع عمومی مستند | بازتولیدپذیری مستقل، بدون تورم مخزن | نیاز به دسترسی به منبع عمومی | مسیر دوم توصیه‌شده برای بازسازی |
| فضای ذخیره‌سازی جداگانه | مناسب حجم‌های بزرگ | وابستگی به سرویس بیرونی | لازم نشد |
| Git LFS | فایل بزرگ در مخزن با مدیریت نسخه | پیکربندی اضافه، سهمیه LFS | لازم نشد؛ حجم کل ۱۲۰ مگابایت است |

**وضعیت فعلی:** داده خام در همین مخزن و در `data/raw/` ثبت شده است (تصمیم قبلی
پروژه). تاریخچه آن حفظ شده و هیچ بازنویسی تاریخی انجام نشده است. اما داده‌های
**میانی و پردازش‌شده** (`data/interim/`, `data/processed/`) در `.gitignore`
هستند، چون بزرگ و کاملاً قابل بازتولیدند.

### یادآوری‌های مهم درباره `.gitignore`

- قرار داشتن فایل در `.gitignore` تنها از **کامیت معمول** جلوگیری می‌کند و به
  خودی‌خود دسترسی محلی را از بین نمی‌برد.
- حذف فایل از `.gitignore` هم به‌تنهایی آن را منتشر نمی‌کند؛ انتشار نیاز به
  `git add` و کامیت دارد.
- پیش از هر تصمیم برای انتشار داده، مجوز استفاده، منبع و ضرورت انتشار بررسی
  شود.

## ۷. کار در وضعیت امروز

اگر روی محیط محلی کار می‌کنید و داده را در جای دیگری دارید:

```powershell
# ویندوز PowerShell - از ریشه مخزن اجرا شود
New-Item -ItemType Directory -Force -Path data\raw | Out-Null
Copy-Item "مسیر\داده\شما\*.csv" -Destination data\raw\
python scripts\validate_data.py
```

هر سه عضو باید همین مسیر را داشته باشند تا مسیرهای نسبی کد کار کنند.
